# Operational monitoring and capacity

`/admin` now polls aggregate operational status every 30 seconds. `/operations` is administrator-only; `/internal/operations` uses the existing service-token guard. Reports contain counts and queue names, not account emails, code, payment data or tokens. The API caches a snapshot for 15 seconds and coalesces concurrent requests. Every minute it writes a structured warning when actionable thresholds are crossed; this is log visibility, not proof that an external pager is configured.

Initial thresholds: oldest pending submission over 5 minutes, any queue over 50 waiting jobs, at least 3 SE verdicts and over 5% SE among verdicts in 15 minutes, unresolved manual refund, or an unexpired account mail challenge with all 5 delivery attempts exhausted. Retained historical BullMQ failures do not independently cause an incident. `judgedAt` is indexed for recent-verdict scans.

The `Production health` GitHub workflow checks `judge.tw` and API health approximately twice an hour, retries transient failures, and fails the workflow if still unhealthy. GitHub schedules may be delayed and repository inactivity/settings may suspend them. Owner notification settings determine whether a failed run is delivered; they are not yet confirmed. No production data or credentials are uploaded as artifacts. This complements platform health checks and is not a 24/7 paging SLA.

`scripts/load-readiness.ts` refuses any database except the isolated localhost test database and refuses a busy test queue. It creates 100 temporary accounts and two exams, exercises concurrent admission, then runs authenticated reads plus 20 submissions/minute across C++, C, Python and Java. A real BullMQ worker invokes production compilation/execution/checking in isolated Docker and posts results back through the built API. It verifies a submission accepted before an exam ends still counts when its real result arrives after completion. It removes only its own fixtures/jobs/sessions. Results in `load-drill.json` distinguish local capacity from Railway/Vercel production capacity.

Railway documents `X-Real-IP` as the client IP header but does not publish a stable socket-peer allowlist in its networking specification. Keep `TRUSTED_PROXY_CIDRS` empty until the origin route is observed. For a short authenticated diagnostic window, set `EDGE_DIAGNOSTICS_ENABLED=true`, call `/internal/operations/edge` with the internal service token, compare baseline against forged X-Real-IP/X-Forwarded-For requests through each actual hostname, and record the trusted socket peer. Do not put the internal token into a browser or public CI secret. Disable diagnostics afterward. Only configure evidenced peer addresses; never trust all sources, arbitrary private ranges, or a fixed proxy-hop count. Recheck after topology changes. [Railway networking specification](https://docs.railway.com/networking/public-networking/specs-and-limits).
