# School verification and practice interactions — 2026-09-17

School confirmation was already bound to the requesting account, but its success screen always linked to authenticated Settings. Opening mail in a separate Chrome profile therefore looked like a failed verification or an unexpected login requirement. The original Settings tab also retained stale auth data, and the MFA/onboarding/deletion overlays could interrupt the public confirmation screen.

The confirmation API now returns only the verified handle and school alongside `ok`, with `Cache-Control: no-store`. The public page identifies that account, distinguishes a different signed-in account, and explains returning to the original browser and sign-in method. It does not create, merge, switch or authenticate accounts. The email includes the requesting handle and the same bilingual instructions. Explicit confirmation, signature/purpose/expiry validation, resend invalidation and unique mailbox claims remain enforced.

A display receipt lasts 30 minutes in the same tab's session storage so refreshing after success is not mistaken for failure. It contains no token, email address, user ID or session credential and authorizes nothing. A new verification link clears the previous receipt. Blocked storage does not prevent confirmation. Pending Settings checks the server on return/focus and every 15 seconds while visible, with a manual retry button. Identity and school/email checks reject stale responses; only the confirmed school timestamp is patched, preserving unsaved profile edits.

The Run button is next to Submit and uses a black background in both themes. A native associated form routes it to the existing sample/custom-input runner. Running opens a separate closable tab in the test pane, focuses and reveals it, and presents output without requiring scrolling past the editable sample. Closing preserves test inputs; Run and Submit retain independent results. Compile/network errors, stale code/language/input results, case limits, empty code and exam locks retain their guards. Mobile exam content uses normal document flow so the editor and results remain reachable.

Submission result headings use English verdict names in either locale, including the requested `Accept` and `Wrong Answer`; the AC/WA tab badges remain unchanged.

The complete exam archive uses compact rows with previews directly underneath. Hover expands the preview in document flow and moves later rows; leaving collapses it. Keyboard focus, Escape and an explicit touch toggle are supported, with reduced-motion preferences respected. The preview contains text only, including ordered labels, titles and UVa IDs. The catalog queries only those fields in one request, excludes private exams, and never retrieves statements, hidden test data or solutions for previews. GPE accent text now follows theme-aware contrast colors.

Validation includes school confirmation under anonymous/original/different/MFA/enrollment/deletion/new-account sessions; retry and fresh-link behavior; Settings focus/manual/poll refresh without losing edits; ordered public catalog exposure; desktop/mobile Run placement, closure, stale results, compile errors and independent English submission verdicts; preview layout expansion/collapse, keyboard/touch, accessibility and reduced motion. Database-dependent tests run against the isolated CI database, never production accounts or real mail.

Pre-push checks: typecheck, lint, API build and production web build passed; 133 non-database tests passed. Production-build browser checks passed 94 cases across Chromium desktop/mobile, Firefox, WebKit desktop and iOS WebKit. Five server-rendered problem checks were skipped locally because the disposable PostgreSQL service did not accept connections; those and 151 opt-in database/sandbox tests remain covered by the release CI environment. Browser screenshots were inspected for the result pane and archive expansion. No production user accounts, mailbox credentials or payment operations were used for these checks.
